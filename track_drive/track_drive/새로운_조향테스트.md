# 새로운 조향테스트

Pure Pursuit + 코너감속 파라미터를 `pp_tune_gridsearch.py`(화이트박스 합성 시뮬레이션)로
재튜닝하는 작업의 진행 기록. **실차 미검증 — 진행 중인 작업 로그**이며, README.md의 정식
버전 히스토리(§0.5.x)와 달리 아직 config.py에 아무것도 반영되지 않은 상태의 원자재 데이터를
모아두는 용도다. 실측속도 확보 + 최종 값 결정 후 README §0.5.x로 정리 이관 예정.

관련 코드: [pp_tune_gridsearch.py](pp_tune_gridsearch.py), [README.md §0.5.14](README.md)

---

## 0. 이번에 시뮬레이터 자체에 생긴 변화 (2026-08-17)

기존 `pp_tune_gridsearch.py`는 직진/90도커브(가정 반경 1.2m)/S자커브(가정 반경 1.3m) 3개를
독립적으로만 채점했다. 이번 세션에서:

1. **실전트랙 시나리오 추가** — 사용자가 제공한 실제 트랙 도면 실측값(좌상단/좌하단 코너
   R1,950mm 동일, 우측 지그재그 구간 R1,615/1,530/1,595/1,470mm 4원호)으로 직진→커브→직진→
   지그재그→직진→커브→직진이 이어지는 연속 경로를 추가. 모드별(long_straight/curve/zigzag)
   cte뿐 아니라 **모드 전환구간**(코너·지그재그 진입/이탈 순간) cte를 따로 집계해 가중치를
   더 준다 — 전환 중에만 유독 튀는 조합을 잡아내기 위함.
2. **`PATH_EMA_ALPHA`(경로 스무딩) 그리드서치 포함** — 실제 `perception/lane_util.py.
   _update_path()`가 매 프레임 새로 피팅된 경로를 직전 프레임 경로와 EMA 블렌딩하는 로직을
   시뮬레이터도 동일하게 재현하도록 추가. 파라미터 총 **22개 → 23개**.
3. **폐루프 앨리어싱 버그 2건 수정** — 실전트랙이 닫힌 루프라 경로상 멀리 떨어진 두 구간이
   월드좌표상 가까워질 수 있는데, `_nearest_point()`(채점용 최근접점)와 `_local_path_px()`
   (센서 웨이포인트 합성)가 둘 다 전역 탐색을 쓰고 있어서 차량이 살짝만 벗어나도 엉뚱한
   구간의 점이 섞여 들어가 조향이 즉시 폭주하는 버그가 있었다. 직전 틱 위치 기준 탐색창
   (`NEAREST_WINDOW_M`)으로 고쳤다. (자세한 내용은 README §0.5.14)
4. **`--optuna` 모드 추가** — 기존 랜덤서치(`--samples`) 대신 Optuna TPE(베이지안 최적화)로
   같은 23차원 공간을 탐색할 수 있게 `run_optuna_search()`/`--optuna --trials N --seed-file
   <json>` 추가. `--seed-file`로 이전 탐색이 찾은 best_params들을 `study.enqueue_trial()`로
   먼저 평가시켜, 새 탐색이 이전 결과를 버리지 않고 그 주변부터 이어서 찾게 한다.
5. **디바운스 파라미터(`DL_STABLE_FRAME_MIN`/`DL_STABLE_JUMP_MAX`) 추가 — 23개 → 25개** —
   "지금까지 설정한 파라미터 중 빼먹은 게 있는지" 사용자 요청으로 실제 코드를 대조하다가
   발견한 진짜 누락. `perception/lane_util.py._debounce()`가 코너 프리뷰 신호(lane_lookahead)
   를 확정하기 전에 거치는 N프레임 연속확인 게이트인데(`PATH_EMA_ALPHA`와는 별개의 스무딩
   단계), 시뮬레이터는 이 게이트 없이 고정 EMA로만 근사하고 있었다. `simulate()`에
   `_debounce()`와 동일한 confirmed/pending/pending_count 상태를 추가해 재현. 이전 라운드
   시드 파일(23키)은 자동으로 두 값의 config.py 현재값(2, 20.0)을 채워서 25차원 시드로
   확장되도록 방어 코드도 추가(`run_optuna_search()`가 `sp.get(k, BASELINE[k])`로 처리) —
   시드 파일을 손으로 갱신할 필요 없음.

### 3차 — Optuna 넓은 속도범위 (완료, 2026-08-17, 23차원 — 4차 디바운스 반영 전)

- **목적**: 실측속도가 아직 불가능(몇 시간 후 가능)한 동안, 실측속도가 어디로 나오든 근처
  값을 바로 쓸 수 있도록 속도 커버리지를 미리 넓혀둔다.
- **명령**: `--optuna --trials 8000 --speeds {5, 7.5} / {12.5, 17.5} / {22.5, 25} --seed 0
  --seed-file <1차+2차 best_params 6개 전부>` (2개 속도씩 묶어 3개 백그라운드 프로세스)

| 속도 | baseline score | best score (8,000 trials) |
|---|---|---|
| 5 | 49.29 | 6.60 |
| 7.5 | 49.29 | 6.32 |
| 12.5 | 50.45 | 6.54 |
| 17.5 | 55.37 | 7.18 |
| 22.5 | 59.12 | 6.93 |
| 25 | 56.36 | 6.72 |

**중요한 발견 — speed=5와 7.5는 사실상 speed=10과 완전히 같은 시나리오였다.** baseline
score(49.29)와 best_params가 speed=10의 2차 결과와 정확히 일치한다. 원인: `config.py`의
`SPEED_CORNER_MIN`은 파일 상단에 `7.0`으로 선언돼 있지만, 하단 `PP_TUNE_ACTIVE_PRESET`
프리셋 적용부가 `globals().update()`로 **10.0**을 덮어써서 실제 로드값은 10.0이다.
`_lane_drive()`의 `target_speed = max(SPEED_CORNER_MIN, speed_norm*(...))` 공식상
speed_norm이 10.0 미만이면 무조건 10.0으로 바닥이 잡혀 speed_norm 자체가 무의미해진다 —
계산이 잘못된 게 아니라 "SPEED_CORNER_MIN=10.0인 한 그 아래 속도들은 전부 speed=10과
동일하게 행동한다"는 걸 실측으로 확인한 것. 이후 재탐색(4차)에서 5/7.5는 별도로 다시
돌리지 않고 speed=10 결과를 그대로 대표값으로 쓴다.

### 4차 — 디바운스 파라미터 추가 + 25차원 재탐색 (완료, 2026-08-17)

- **계기**: 사용자가 "지금까지 설정한 조향 파라미터 중 빼먹은 게 있는지" 확인 요청 →
  코드 대조 중 `DL_STABLE_FRAME_MIN`/`DL_STABLE_JUMP_MAX`(코너 프리뷰 신호의 N프레임
  디바운스, §0.5 참고)가 진짜로 빠져있었던 것을 발견. 파라미터 **23개 → 25개**.
- **재계산 전략**: 새 차원이 추가되면 1~3차 결과는 "다른(더 단순한) 시뮬레이터 버전"에서
  나온 값이라 점수가 직접 비교 가능하지 않다 — 그렇다고 처음부터 다시 찾을 필요는 없고,
  1~3차가 찾은 best_params들을 새 2개 파라미터만 config.py 현재값(2, 20.0)으로 채운 뒤
  Optuna 시드로 그대로 재사용한다(`run_optuna_search()`의 `sp.get(k, BASELINE[k])` 방어
  코드로 자동 처리 — 시드 파일을 손으로 안 고쳐도 됨).
- **자원 제약**: 이 개발 PC가 성능코어 4개라 2단계로 나눠 진행:
  - **1단계(진행 중)**: 시드가 가장 풍부한 speed 10/15/20을 1차+2차 best_params 6개로
    시드해 `--optuna --trials 6000 --speeds 10 15 20 --seed 0 --seed-file <1차+2차 6개>`
    실행.
  - **2단계(진행 중, 3차 완료로 코어 확보)**: 3차가 끝나 speed=5/7.5는 speed=10과 동일
    시나리오임이 확인됐으므로(위 3차 "중요한 발견" 참고) 별도로 다시 안 돌리고, 실제로
    구분되는 4개 속도(12.5/17.5/22.5/25)만 1차+2차+3차 best_params 10개(5/7.5 제외
    중복 제거)를 전부 시드로 넣어 `--optuna --trials 8000 --speeds {12.5,17.5} /
    {22.5,25} --seed 0 --seed-file <10개>` 2개 프로세스로 실행.
- **상태**: 완료. speed=5/7.5는 speed=10과 동일 시나리오라 별도 실행 없이 그 값을 대표로 씀.

|---|---|---|
| 5 | 6.60 | (=10과 동일) |
| 7.5 | 6.32 | (=10과 동일) |
| 10 | 6.59 | **6.83** |
| 12.5 | 6.54 | **6.47** |
| 15 | 6.95 | **7.15** |
| 17.5 | 7.18 | **7.04** |
| 20 | 6.99 | **6.96** |
| 22.5 | 6.93 | **6.76** |
| 25 | 6.72 | **6.91** |

**결론 1 — 디바운스 파라미터를 추가해도 기존 핵심 결론이 뒤집히지 않았다.** 점수가 전부
6.4~7.2 사이로 23차원 때와 오차범위 안에서 비슷하다. 즉 빠져있던 파라미터가 최적해 자체를
크게 바꿀 만큼 중요하진 않았다 — 다만 이건 "몰라도 됐다"가 아니라 "이번 시뮬레이션 설정
안에서는 다른 23개가 이미 지배적이었다"는 뜻이라, §0에서 지적한 대로 여전히 그리드서치
대상에 넣어두는 게 맞다.

**결론 2 — `path_ema_alpha`가 9개 속도 전부에서 놀라울 정도로 좁게 수렴했다(0.748~0.800).**
지금까지 나온 것 중 가장 강한 신호다 — 속도와 사실상 무관하게 config.py 현재값(0.25)보다
3배 가까이 높은 값을 일관되게 원한다는 뜻. `lookahead_base_px`(77~84)/`wheelbase_px`
(45~50, speed=22.5만 45.16으로 소폭 예외)/`alpha`(대부분 0.82~0.95, speed=12.5만 0.75)도
비슷하게 좁은 범위로 수렴했다.

**결론 3 — 새로 추가한 `stable_frame_min`/`stable_jump_max`는 속도별로 흩어져 있고
(2~10 프레임, 10~58px) 점수에 미치는 영향도 상대적으로 작아 보인다.** 이 둘은 "빠뜨리면
안 되는 파라미터"이긴 했지만 "결과를 좌우하는 핵심 파라미터"는 아니었다는 뜻 — 코너감속
계열(`corner_sign_ema_alpha`/`lane_lookahead_ref`/`speed_corner_min`)도 여전히 흩어져
있는데, 그중 `corner_min_radius_px`만 865(10)→418(12.5)→567(15)→235(17.5)→217(20)→
197(22.5)→374(25)로 노이즈는 있지만 대체로 속도가 오를수록 낮아지는 경향이 보인다 —
게인 스케줄링(사용자가 물었던 "속도에 따라 파라미터를 가변화") 후보로 가장 유력해 보이나,
아직 진짜 추세인지 노이즈인지 `--sensitivity`로 재확인 필요.

## 2. 핵심 발견 / 주의사항

1. **`wheelbase_px`(25.0→~43~50)와 `path_ema_alpha`(0.25→~0.59~0.79)는 최근 커밋이 정확히
   반대 방향으로 낮췄던 값이다.**
   - `e86c023`: "speed15 프리셋 PP_WHEELBASE_PX 47.36→25.0 — 좌우 진동 원인"
   - `936dcd7`: "PATH_EMA_ALPHA 0.75 → 0.25(요청 반영)"
   시뮬레이션이 실제 트랙 곡률(실전트랙)을 처음 반영하면서 독립적으로 "그때 낮췄던 게
   과했다"는 방향의 결론에 세 번(1차 3속도) 다 도달했고, 2차(Optuna)에서 세 속도 모두
   거의 같은 값(~48~49 / ~0.72~0.79)으로 더 강하게 수렴했다. 방향이 일관될수록 흥미롭긴
   하지만, **정확히 실차 진동 문제로 낮췄던 값을 되돌리라는 결과라 실차 재검증 없이는
   절대 그대로 적용 금지.**
2. **시뮬레이션 자체의 한계**(스크립트 상단 주석 원문 그대로): 세그멘테이션 노이즈
   1.5px(가정), `DL_PIXELS_PER_METER=200px/m`(설계값), 지그재그 4원호의 회전각(도면에
   반지름만 있고 각도는 없어 `ZIGZAG_WIGGLE_DEG`로 임의 가정), VESC/IMU 미시뮬레이션(항상
   `_prev_speed` 폴백 경로만 검증), 모터/서보 반응 지연·배터리 전류 전혀 미모델링. 전부
   README §0.5.12/§0.5.14가 이미 명시한 한계와 동일한 종류.
3. **speed20(및 그 이상)은 `METERS_PER_SPEED_UNIT` 실측 회귀구간(speed 5~10) 밖 외삽**이라,
   이 구간에서 코너감속 파라미터가 유독 크게 흩어지는 게 진짜 속도 의존성인지 회귀 외삽
   오차인지 아직 구분 안 됨.
4. **config.py에는 지금까지 아무것도 반영 안 됨** — README §0.5.12/§0.5.13이 지켜온 절차
   (정식 실행 + 사용자 확인 후에만 반영)를 그대로 따름.
