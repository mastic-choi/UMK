## 1. 문제 정의

- **증상**: 차선 중앙 부근에서 조향이 좌우로 계속 미세하게 흔들림("와리가리"). `README.md`
  §0.5.3에서 "진동 자체"가 아니라 "진동 때문에 속도가 같이 출렁이는 것"은 이미 대응했지만,
  조향 진동 자체(`self.ctrl_angle`)는 근본적으로 남아있음(§0.5.3 알려진 한계 참고).
- **근본 원인**: 조향 컨트롤러(Pure Pursuit)가 아니라, 그 입력인 `self.lane_path`가 매 프레임
  독립적으로 새로 피팅되기 때문 — da/ll 세그멘테이션 자체의 프레임간 노이즈가 그대로 경로에
  실림.
- **설계 원칙(이 논의 전체에 깔린 전제)**: 컨트롤러(Pure Pursuit)는 이미 실차 라바콘 구간까지
  검증된 유일한 검증된 조합이므로 **바꾸지 않는다**. 대신 (a) 컨트롤러에 들어가는 입력을
  깨끗하게 만들거나, (b) 컨트롤러가 내놓는 출력에 안전장치를 씌우는 방향으로 접근한다. 이렇게
  하면 "인식 노이즈 때문인지 컨트롤러 튜닝 때문인지" 원인이 섞이지 않는다.

## 2. [설계됨, 미구현] 경로 스무딩: EMA → 칼만필터

**무엇**: 현재 `perception/lane_util.py`의 `SlideWindow._update_path()`는 웨이포인트
인덱스별로 새 값과 직전 값을 고정 비율(`PATH_EMA_ALPHA`, 현재 0.4)로 섞는 EMA 방식이다.
이걸 웨이포인트마다 등속도(위치+속도) 모델로 상태추정하는 1D 칼만 필터로 교체하는 안.

**EMA의 구조적 한계**: "부드러움"과 "반응속도"가 alpha 하나에 묶여 있어서, 흔들림을 줄이려고
alpha를 낮추면 코너 진입 같은 실제 경로 변화에 대한 반응도 같이 늦어진다 — `README.md`
§0.5의 lookahead 관련 여러 절이 전부 이 트레이드오프 안에서의 미세조정이었다.

**칼만 필터가 다른 점**: 위치뿐 아니라 "속도"(변화율)도 같이 추정한다.
- 순수 노이즈만 있는 프레임(실제 경로는 안 바뀜) → 속도 상태가 0 근처에 머물러 예측이 계속
  실측과 어긋나지 않으므로, 필터가 측정을 적게 반영한다(EMA보다 더 부드러워질 수 있음).
- 경로가 실제로 이동하는 프레임(코너 진입 등) → 속도 상태가 그 추세를 따라잡아 예측 자체가
  실측에 가까워지므로, 다음 프레임의 반응 지연이 EMA보다 작아질 수 있다.
- "얼마나 반영할지"가 매 프레임 자동으로 조정된다는 게 핵심(EMA는 항상 고정 비율).

**적용 위치**: `perception/lane_util.py`의 `SlideWindow` — `_update_path()`를 수정하고,
`_kf_reset()`(웨이포인트별 트랙 초기화)/`_kf_smooth_path()`(측정값 반영) 메서드와 모듈 함수
`_kalman_step()`(등속도 1D 칼만 필터 한 스텝, 트랙 N개를 벡터화해 한번에 처리)을 추가한다.
`SlideWindow`가 공통 기반 클래스이므로 dl 백엔드(`DLSlideWindow`, 현재 기본값)와 classic_cv
백엔드 둘 다 오버라이드 없이 자동으로 적용받는다.

**칼만 필터 한 스텝 수식(등속도 모델, dt=1프레임)**:
```
예측: x_pred = x + vx,  vx_pred = vx
      P_pred = F P F^T + Q   (F=[[1,1],[0,1]], Q=diag(q_pos, q_vel))
갱신: innovation = z - x_pred
      S = P_pred[0,0] + r
      K = P_pred H^T / S     (H=[1,0], 위치만 관측)
      x_new = x_pred + K0*innovation
      vx_new = vx_pred + K1*innovation
      P_new = P_pred - K H P_pred
```
x/y 좌표 각각에 독립적으로 적용(두 축의 상관관계는 반영하지 않음 — EMA도 x/y를 독립적으로
블렌딩했던 것과 같은 수준에서 시작).

**필요 설정값(신설 예정, `config.py`, 전부 실차 미검증 첫 추정치)**:
```python
PATH_SMOOTHING_MODE = 'kalman'  # 'ema' | 'kalman' — 문제 생기면 'ema'로 즉시 롤백 가능하게
PATH_KF_Q_POS = 4.0     # 프로세스 노이즈(위치) — 클수록 모델보다 실측을 더 믿음(반응↑, 노이즈 민감도↑)
PATH_KF_Q_VEL = 1.0     # 프로세스 노이즈(속도) — 클수록 가속/코너 진입을 더 빨리 따라잡음
PATH_KF_R = 64.0        # 측정 노이즈 — 클수록 필터가 더 느리게(부드럽게) 반응
PATH_KF_INIT_VAR = 10000.0  # 트랙 재초기화 시 초기 불확실성 — 크게 잡아 첫 프레임은 실측을 거의 그대로 신뢰
```

**무효 프레임 처리 원칙**: 유효 슬라이스 2개 미만이라 `fitted_path`가 None인 프레임에는
predict 단계조차 건너뛰고 완전히 정지시킨다(EMA의 "무효 프레임엔 마지막 값 유지"와 동일한
정신 — 무효 프레임이 여러 프레임 이어질 때 속도 상태만으로 예측이 계속 벌어지는 걸 방지).

**구현 시 체크리스트**:
1. `config.py`에 위 5개 상수 추가.
2. `perception/lane_util.py`에 모듈 함수 `_kalman_step()` 추가, `SlideWindow.__init__`에
   웨이포인트별 상태(x, vx, p00, p01, p11 — x/y 각 3개 공분산 항, 총 10개 배열) 초기화 필드
   추가, `_update_path()`가 `PATH_SMOOTHING_MODE`로 EMA/칼만 분기하도록 수정.
3. 첫 프레임/웨이포인트 개수 변경 시 트랙 재초기화(`_kf_reset`) 로직 필요.

**알려진 한계**:
- 튜닝값(Q, R)이 EMA(파라미터 1개)보다 많고 의미가 덜 직관적이라 처음 맞추기 어렵다.
- x/y 독립 처리라 두 축 상관관계는 반영 못 함(이론적으로는 2D 결합 모델이 더 정확할 수 있음).
- "제대로 튜닝됐을 때" 이점이 나오는 것이라, 초기값이 부적절하면 EMA보다 오히려 나쁘게
  동작할 수 있다 — 실차 확인 없이는 "더 낫다"고 단정할 수 없음.

## 3. [설계됨, 미구현] 조향각 슬루레이트 리미터 (출력단 하드 캡)

**무엇**: 조향각이 "한 틱(1/20초)에 최대 몇 도까지만" 바뀔 수 있게 절대 상한을 씌우는 필터.

```python
diff = clip(raw_steer_deg - prev_steer_deg, -MAX_STEP_DEG, +MAX_STEP_DEG)
steer_deg = prev_steer_deg + diff
```

**칼만필터/EMA와 다른 점**: 둘 다 "새 값을 몇 % 반영할지" 비율로 정하는 방식이라, 입력이
극단적으로 튀면(예: 인식 완전 오검출) 반영되는 절대량도 같이 커진다. 슬루레이트 리미터는
비율이 아니라 **변화량 자체에 상한**을 걸기 때문에, 입력이 아무리 극단적이어도 한 틱에 정해진
각도 이상은 절대 못 바뀐다는 확정적(deterministic) 보장이 생긴다.

**적용 위치**: `controller/pure_pursuit.py`의 `PurePursuitController.control()` 마지막
부분(`self.alpha` EMA를 적용하는 지점, 현재 `steer_deg = self.alpha * steer_deg + (1.0 -
self.alpha) * self.prev_steer_deg` 줄) — **이 EMA를 슬루레이트 리미터로 교체**하는 것을
권장(아래 이유).

**주의 — 기존 `self.alpha`(EMA)와의 관계**:
- 지금 `self.alpha=0.5`짜리 EMA가 이미 같은 위치에서 "조향각 저역통과" 역할을 하고 있다.
- §2(경로단 칼만필터)가 실제로 적용되면, 여기서 또 EMA를 걸어 같은 종류의 스무딩을 두 번
  하는 셈(중복)이라 반응만 둔해진다.
- 슬루레이트 리미터가 하는 일(극단값에 대한 하드 캡)은 EMA/칼만필터 어느 쪽도 보장하지
  못하는, 채워지지 않은 빈틈이다.
- **권장 조합**: 경로 스무딩 = 칼만필터(§2, 입력단) + 조향각 = 슬루레이트 리미터(출력단) —
  `self.alpha` EMA는 제거하거나 사실상 무력화(`alpha=1.0`)한다.

**필요 설정값(신설 예정, `config.py`)**:
```python
PP_STEER_SLEW_MAX_DEG_PER_TICK = ???  # 실차 미검증 — 실제 서보 반응속도/타이어 그립 한계를
                                        # 보고 정해야 함. 너무 낮으면 급코너 대응이 늦어짐.
```

**구현 시 체크리스트**:
1. `PurePursuitController.__init__`에 `steer_slew_max_deg` 파라미터 추가(기존 `alpha`
   파라미터와 나란히 두거나 대체).
2. `control()` 마지막의 EMA 블렌딩 줄을 슬루레이트 클램프로 교체.
3. `self.reset()`이 `prev_steer_deg`를 0으로 되돌리는 기존 동작은 유지(리미터 상태도 같이
   초기화되는 셈이라 별도 처리 불필요).
4. LQR 컨트롤러(`controller/lqr.py`)에도 같은 문제가 있는지 확인 — `LQR_ALPHA`도 동일한
   EMA 패턴이라, 슬루레이트 리미터를 쓰기로 결정하면 LQR 쪽도 일관되게 맞출지 검토.

## 4. [설계됨, 미구현] 칼만필터 공분산 → 속도 감속 연동

**선행조건**: §2(경로 스무딩 칼만필터)가 먼저 구현/검증돼야 한다 — 이 항목이 쓰는 공분산은
그 필터의 부산물이기 때문.

**아이디어**: 칼만필터는 위치/속도 추정치 외에 "지금 이 추정을 얼마나 믿을 수 있는지"를
나타내는 공분산(§2에서 계산될 `p00` 계열)을 같이 갖는다. 이 값이 크다는 건 "최근 몇 프레임
인식이 계속 흔들려서 필터가 확신을 못 하고 있다"는 뜻이므로, 이걸 속도 계획에 넘겨서 불확실할
때 자동으로 감속하게 만들 수 있다.

**기존 패턴과의 일관성**: 이미 `_corner_radius_speed_scale()`(회전반경 기반 감속),
`DL_LL_SANITY_MIN_RATIO`(ll 커버리지 부족 시 프레임 무효화) 같은 "불확실/위험하면 감속·무효화"
패턴이 이 프로젝트에 여러 번 쓰였다 — 같은 철학의 연장.

**설계 스케치**:
```python
# perception/lane_util.py, SlideWindow 어딘가에 노출 (§2 구현 이후)
self.path_uncertainty = float(np.mean(self._kf_p00x)) if self._kf_p00x is not None else 0.0

# track_drive.py _lane_drive() 또는 속도 계획 쪽에서
uncertainty_scale = clip(1.0 - K * path_uncertainty, SPEED_UNCERTAIN_MIN_SCALE, 1.0)
target_speed *= uncertainty_scale
```

**필요 설정값(신설 예정)**: `SPEED_UNCERTAIN_GAIN`(K), `SPEED_UNCERTAIN_MIN_SCALE` — 둘 다
실측 필요(공분산 값의 실제 스케일을 먼저 로그로 찍어봐야 K를 가늠할 수 있음).

## 5. [설계됨, 미구현] IMU-비전 상보 필터 (offset 융합)

**아이디어**: §2의 칼만필터는 "비전 경로점 하나"를 그 자체의 노이즈만으로 다듬는다(입력 1개).
상보 필터는 성질이 다른 **두 신호**를 섞는 방식이라, 비전(장기적으로 정확, 프레임마다 노이즈)과
IMU(순간 반응 빠름, 적분하면 드리프트)를 결합할 때 쓴다.

**이미 있는 재료**: `track_drive.py`에 `self.imu_yaw`, `self.imu_yaw_rate`가 이미 있고,
`pure_pursuit.control()`이 `imu_curvature_px`를 받아 코너 감쇠에 쓰고 있다(§0.5.4, README).
즉 배선은 이미 돼 있고, 지금은 "감쇠 판단"에만 쓰는 걸 "실제 offset 보정"까지 확장하는 것.

**설계 스케치(개념)**:
```python
# 매 제어 틱(20Hz)마다:
# 1) IMU yaw_rate를 적분해서 "짧은 시간 동안 얼마나 회전했는지" 추정 → 그만큼 lane_offset을
#    미리 보정(카메라 프레임이 아직 안 갱신된 사이의 공백을 메움)
# 2) 새 비전 프레임이 도착하면, 그 실측 offset으로 다시 강하게 잡아당김(저주파 성분은 비전이
#    항상 이김 — IMU 드리프트가 누적되지 않게)
predicted_offset += imu_yaw_rate * dt * GAIN   # 고주파(즉각 반응)는 IMU
offset_filtered = COMP_ALPHA * predicted_offset + (1 - COMP_ALPHA) * vision_offset  # 저주파는 비전
```

**전제 조건**: IMU 드리프트 특성(가만히 있을 때 `imu_yaw_rate`가 실제로 얼마나 흔들리는지)을
실측해야 시상수(`COMP_ALPHA` 또는 시간상수)를 제대로 잡을 수 있다 — 아직 실측 안 됨.

**우선순위**: §3/§4보다 낮음 — 카메라가 20Hz 제어 루프보다 느릴 때(DL 추론 지연) 체감 효과가
가장 클 텐데, 지금 얼마나 느린지 실측 로그부터 필요하다.

---

## 6. [보류] 컨트롤러 자체 교체 (MPC / Stanley / LQR)

- **Stanley/LQR**: 이미 `controller/stanley.py`, `controller/lqr.py`로 구현돼 있고
  `config.py STEERING_CONTROLLER` 스위치로 전환 가능. 다만 지금 논의의 결론은 "검증된
  Pure Pursuit은 그대로 두고 입력/출력만 다듬는다"였으므로, 컨트롤러 자체를 바꾸는 건 이번
  개선 방향에서 **제외**했다. 필요해지면 별도 A/B 테스트로 접근할 것.
- **MPC(모델예측제어)**: 조향각 변화율(jerk)을 목적함수에 직접 넣어 억제할 수 있어 안정성
  문제엔 교과서적 정답이지만, 매 틱 최적화 계산이 필요해 지금 하드웨어(20Hz 루프,
  Jetson급 보드로 추정)엔 부담되고 새로 통째로 설계/튜닝해야 해서 **이 프로젝트 규모엔
  오버스펙**으로 판단, 보류.

## 8. 권장 진행 순서

1. **[§2 구현]** 경로 스무딩을 칼만필터로 교체하고 실차 검증 → `DEBUG_VIZ_DL_LANE`/
   `steer_debug`로 직선 잔떨림·코너 반응 지연을 `'ema'`와 비교. 문제 있으면 `PATH_KF_Q_POS`/
   `PATH_KF_Q_VEL`/`PATH_KF_R` 재조정, 그래도 안 되면 `'ema'`로 롤백.
2. **[§3 구현]** 슬루레이트 리미터를 `pure_pursuit.py`에 추가하고 `self.alpha` EMA 제거/무력화.
   `PP_STEER_SLEW_MAX_DEG_PER_TICK` 값은 저속·개입 가능 상태에서 보수적으로 시작해 점점
   올리며 찾을 것.
3. **[§4 구현]** 1, 2가 안정화된 뒤 공분산→감속 연동 추가(부가 기능이라 우선순위 낮음).
4. **[§5 검토]** IMU 드리프트 실측 후 필요성 재평가.

각 단계 구현 완료 시 `README.md`의 §2 계열(또는 새 번호)로 증상/원인/수정/알려진 한계
포맷에 맞춰 옮겨 적을 것 — 이 문서는 임시 설계 메모이고, `README.md`가 이 프로젝트의
공식 "살아있는 설계문서"다.
