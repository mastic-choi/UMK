# avoid-hold 개선 — 실측 필요 파라미터 + 측정 절차 (2026-08-15)

**상태: 코드는 구현 완료(README §2.33, `avoid_hold_improvement_proposal.md` "1차 적용
결정"), 아래 6개 파라미터는 전부 첫 추정치 — 실차 실측 전까지 근거 없는 값으로 취급할
것.** `measure_lidar_camera_offset.md`와 같은 성격의 "실측 how-to" 문서 — 이 도구는 없고
전부 실차에서 `DEBUG_VIZ_AVOID_HOLD`(신규, `avoid_hold_debug` 창)로 직접 관찰/기록하는
방식이다.

## 공통 준비물

- `config.py`에서 `DEBUG_VIZ_AVOID_HOLD = True`(기본값이 이미 True). 회피 관련 다른 창도
  같이 켜두면 교차확인에 도움됨 — `DEBUG_VIZ_LIDAR`(lidar_bev, obstacle_dist 실측 확인),
  `DEBUG_VIZ_DL_LANE`(dl_lane, da/ll 실제 검출 확인), `DEBUG_VIZ_VESC`(vesc_debug, v_mps
  실측 확인).
- `avoid_hold_debug` 창에 뜨는 값 자체가 이 문서가 요구하는 관측값 대부분이다 — 화면을
  녹화해두면(또는 스마트폰으로 촬영) 나중에 프레임 단위로 다시 보며 숫자를 옮겨적을 수
  있다. `DEBUG_LOG=True`(기본값)면 터미널 로그에도 0.5초 주기로 관련 값이 찍히니 병행
  가능.
- 아래 절차들은 **B2(고정장애물)/B3(방해차량) 상황을 각각 여러 번 재현**하는 게 핵심이다
  — `TEST_DISABLE_B2_B3=True`(현재값)라 정식 미션 트리거는 안 걸리지만, avoid-hold
  자체는 이 플래그와 무관하게 라이다 `obstacle_front`만으로 동작하므로(README §2.32
  배경) 트랙 위에 장애물(정지 박스, 또는 사람이 천천히 미는 다른 RC카/물체)을 그냥
  놓고 지나가기만 해도 재현할 수 있다.

## 1. `AVOID_HOLD_RATE_GAIN`, `AVOID_HOLD_SEC_MAX` (같이 측정)

**뭘 정하는 값인가:** `hold_sec = clip(BASE + RATE_GAIN*|target_speed_est|, MIN, MAX)` —
상대속도가 빠를수록 유예를 얼마나 더 늘릴지(GAIN)와, 아무리 빨라도 어디서 멈출지(MAX).

**절차:**
1. 정지 장애물(B2)을 여러 번 통과하며, 트리거 순간 `avoid_hold_debug` 창의
   `target_speed_est(트리거 스냅샷)` 값을 기록한다 — 정지 장애물이면 이 값이
   `OBSTACLE_STATIC_SPEED_TH_MPS`(0.3) 이하로 나와야 정상. 그렇지 않으면 GAIN을
   튜닝하기 전에 `obstacle_rate` 계산 자체(라이다 노이즈, `perc_obstacle()`의
   `dt_o`)부터 재점검할 것.
2. 방해차량 역할(대회 규정 속도로 사람이 밀거나 원격 조종하는 다른 물체)을 여러 번
   통과하며 같은 값을 기록 — 이번엔 0에서 뚜렷이 벗어난 값이 나와야 정상. 최댓값/평균을
   구한다.
3. "이 정도 상대속도면 이만큼(초) 유예가 적당하다"는 감각을(대회 규정상 방해차량 추월 후
   복귀 여유, §5 "90cm 이상 벌어지면 이탈판정"과 균형 맞춰) 정하고, 관측된
   `target_speed_est` 최댓값에서 그 hold_sec이 나오도록 `RATE_GAIN`을 역산한다:
   `GAIN ≈ (원하는_hold_sec − BASE) / 관측된_target_speed_est_최댓값`.
4. `SEC_MAX`는 위에서 역산한 hold_sec보다 살짝만 여유를 둔다 — 지나치게 크면 §2.32/§2.33
   한계에 적힌 "불안정한 ll클리핑 경로에 오래 끌려다니는" 리스크와 대회 규정의 "복귀
   지연" 리스크가 같이 커진다.
5. 설정 후 다시 통과시켜보며 `avoid_hold_debug`의 `hold_sec` 표시값이 기대 범위에서
   나오는지, `직전 해제 사유`가 정지 장애물에선 대부분 `timeout`(1번 절차 참고), 빠른
   방해차량에선 `timeout` 또는 `early_dist` 중 상황에 맞게 나오는지 재확인한다.

## 2. `AVOID_HOLD_RELEASE_DIST_M`

**뭘 정하는 값인가:** "이 거리 이상이면 진짜로 안전하게 원래 차선 중앙으로 돌아가도
된다"는 문턱.

**절차:**
1. 장애물을 통과한 뒤 `obstacle_dist`가 점점 벌어지는 걸 `avoid_hold_debug`(또는
   `lidar_bev`)에서 지켜보며, 사람이 육안으로 "지금이면 안전하게 복귀해도 된다"고
   판단되는 순간의 `obstacle_dist` 값을 여러 번(정지 장애물/방해차량 각각) 기록한다.
2. 방해차량 시나리오에서는 특히 신중하게 — 너무 짧게 잡으면 아직 옆에 있는데 복귀해
   추돌 위험(§2.32 배경 그대로), 너무 길게 잡으면 대회 규정 "90cm 이상 벌어지면 오히려
   차선이탈 판정"(§5 방해차량 추월 규정)과 충돌할 수 있다 — 이 둘 사이의 값을 찾는 게
   목표.
3. 기록된 샘플들의 평균에서 표준편차만큼 보수적으로 낮춘(=더 오래 붙어있는 쪽) 값을
   최종 후보로 삼는다. 초기값 2.0m을 기준점으로 위아래 조정.
4. `AVOID_HOLD_TRIGGER_DIST_M`(1.5m)보다는 반드시 커야 한다 — 안 그러면 히스테리시스가
   없어져 트리거/해제가 경계에서 진동할 수 있다.

## 3. `AVOID_HOLD_DA_AREA_JUMP_RATIO`

**뭘 정하는 값인가:** da(주행가능영역) 채택 덩어리 면적이 "그냥 세그멘테이션이 흔들린
것"과 "진짜로 장애물이 시야에서 사라져 구멍이 메워진 것"을 가르는 배율 문턱.

**절차:**
1. `DEBUG_VIZ_DL_LANE` + `DEBUG_VIZ_AVOID_HOLD`를 같이 켜고, **장애물이 전혀 없는**
   평범한 직선/코너 주행 중 `avoid_hold_debug`의 `chosen_area=...px` 값이 프레임마다
   최대 몇 배까지 흔들리는지 관찰해 "노이즈만으로 나오는 배율 상한"을 기록한다.
2. 장애물을 실제로 통과하는 상황을 여러 번 재현하며, 장애물이 시야에서 사라지는 그
   순간 `chosen_area` 값이 직전 대비 실제로 몇 배로 뛰는지(`jump=O`로 바뀌는 시점 전후
   값) 기록해 "진짜 이벤트일 때의 배율 하한"을 구한다.
3. 1의 상한 < `AVOID_HOLD_DA_AREA_JUMP_RATIO` < 2의 하한이 되도록 설정한다.
4. **두 범위가 겹치면**(노이즈만으로도 실제 이벤트만큼 크게 흔들리면) 이 보조 신호
   자체를 신뢰하기 어렵다는 뜻이다 — `avoid_hold_improvement_proposal.md` 문제3 대비책에
   이미 적어둔 리스크가 실제로 발현된 경우이므로, 이 경우엔 임계값을 조정하는 대신 적용2
   (da 연속성 보조트리거) 자체를 끄는 것도 고려할 것(라이다 단독 트리거로 되돌아가는
   것과 동일 — `_update_avoid_hold()`의 `da_area_jump` OR 조건 부분만 주석 처리하면 됨).

## 4. `AVOID_HOLD_DIR_BIAS_PX` (비율)

**뭘 정하는 값인가:** ll/잔상이 전혀 없는 최후수단(가상경계) 상황에서, 방향 힌트 쪽으로
기준점을 얼마나 세게 밀어둘지(px). 너무 작으면 효과가 없고, 너무 크면 반대편 실선 밖으로
da를 밀어버릴 위험이 있다.

**절차:**
1. 먼저 픽셀 산수로 안전선을 확인한다 — `DEBUG_VIZ_DL_LANE`의 `dl_lane` 창에서
   `_ll_active_half_width()`의 실제 표시값("gap" 표시, README §2.19/§2.24 등에서 이미
   실측 관례가 있음)을 확인하고, `AVOID_HOLD_DIR_BIAS_PX`가 그 절반을 넘지 않는지 확인한다
   (넘으면 반대편 차선 경계를 넘어갈 수 있음).
2. 이 최후수단 분기는 ll이 잘 잡히는 정상 상황에선 거의 안 쓰인다 — 일부러 재현하려면
   ll 인식이 약한 구간(조명이 안 좋은 구간, 원거리 등)에서 avoid-hold를 걸어본다.
3. `dl_lane` 디버그 창의 태그(`[AVOID_HOLD dir:R]`/`[AVOID_HOLD dir:L]`)가 뜨는 프레임의
   실제 클리핑 오버레이가 의도한 방향으로 자연스럽게 쏠리는지 육안으로 확인하며 값을
   조정한다 — 반대쪽 실선을 넘어가지 않는 선에서 가장 자연스러운 값을 채택.

## 5. `SPEED_AVOID_HOLD_BLOCKED`

**뭘 정하는 값인가:** avoid-hold 중 `choose_side()`가 "양쪽 다 막힘"(0)을 반환할 때
강제로 낮추는 속도 — 모터 데드존 위에서 눈에 띄게 느리지만 완전정지는 아닌 값.

**절차:** 새로 만들 절차 없이 README §6.5(단위환산, `PIXELS_PER_METER`/
`METERS_PER_SPEED_UNIT` 실측 회귀)와 **동일한 방법론을 그대로 재사용**한다 — 여러 speed
명령값에 대해 VESC 실측 m/s(`v_mps`, `DEBUG_VIZ_VESC`의 `vesc_debug` 창)를 재서 회귀선을
그리고, 그 절편(모터 데드존 추정치)보다 확실히 위인 값을 고른다. `SPEED_CORNER_MIN`/
`SPEED_LL_DEGRADED`/`SPEED_LANE_STALE`이 전부 이 방법으로 이미 `5.0`을 채택해뒀으므로,
**우선 그 값을 그대로 쓰고**, 실차에서 "avoid-hold 안전판이 걸렸을 때 실제로 눈에 띄게
느리지만 정지는 안 하는지"만 확인한다 — 코너/ll저신뢰/lane_stale과 "양쪽 다 막힘" 상황이
위험도 면에서 동등하게 취급해도 되는지도 같이 재확인할 것(더 위험하다고 판단되면 더
낮출 것).

---

## 측정 후 반영 순서

1. 위 5절차로 얻은 값을 `config.py`의 각 `AVOID_HOLD_*`/`SPEED_AVOID_HOLD_BLOCKED` 주석에
   "★실측 필요★" 표시를 지우고 실측 근거(날짜/방법/샘플 수)를 남기며 갱신한다 — 이
   저장소 관례(다른 실측값들의 주석 스타일 참고, 예: `LANE_WIDTH_M`/`VEHICLE_WIDTH_M`).
2. `avoid_hold_debug` 창의 "★ 실차 미검증 ★" 구간에서 반영이 끝난 파라미터는 지우거나
   색을 정상(흰색)으로 바꾼다(`track_drive.py` `_debug_viz_avoid_hold()`의 `UNMEASURED`
   리스트에서 제거).
3. README §2.33 "알려진 한계"의 "실측 필요 6개 파라미터는 첫 추정치" 문구를 실측 완료
   상태로 갱신한다.
