# ll 확률값 가중치 기반 계산 — 제안 (미구현, 2026-08-07)

**상태: 설계 제안 단계, 코드에 아직 반영 안 됨.** 먼저 `DL_LL_FG_THRESHOLD`를 0.7→0.5로 낮추는
값 조정(README §2.15)을 실차에서 확인하고, 그걸로도 ll 검출 흔들림/부족이 남을 때 이 방향을
검토할 것.

## 배경

`perception/dl_lane.py`의 `detect()`는 TwinLiteNet이 뱉는 `ll_prob`(픽셀마다 0.0~1.0 연속
확률값)를 `DL_LL_FG_THRESHOLD` 하나로 이진화(`ll_mask = (ll_prob >= threshold) * 255`)한
뒤, 그 이후 파이프라인 전부(`_ll_slice_centers()`의 `cv2.moments`, 픽셀수 카운트
`DL_LL_SIDE_MIN_PIXELS`, `_clip_da_by_ll()`의 `np.nonzero` 등)가 이 이진 마스크만 보고
동작한다.

## 현재(이진화) 방식의 근본적 한계

확률 0.49와 0.51은 모델 입장에서 사실상 같은 신뢰도인데, 이진화하면 하나는 완전히
"없음"(0), 하나는 완전히 "있음"(255)으로 갈린다. 프레임마다 노이즈로 이 경계를 오가는
픽셀은 그대로 "이 밴드에 ll이 잡혔다/안 잡혔다"가 반복되는 흔들림으로 이어진다 — 오늘
세션에서 계속 다룬 da/ll 흔들림 문제의 원인 중 하나일 수 있다.

또한 원거리일수록 BEV 워프가 확률맵 경계 blur를 확대하는 문제(§2.2)가 있어서
`DL_LL_FG_THRESHOLD`를 da(`DL_FG_THRESHOLD=0.5`)보다 높게(0.7) 잡아뒀었는데, 이번에
실차 영상을 보니 그 임계값이 너무 높아 정상 신뢰도(0.5~0.7)의 실제 차선 픽셀까지
걸러내고 있었을 가능성이 확인됐다(README §2.15). 즉 **"근거리엔 낮은 임계값, 원거리엔
높은 임계값"이 이상적인데 지금은 숫자 하나로 그 타협을 봐야 하는 구조**라는 것 자체가
근본 원인이다.

## 제안: 이진화를 없애고 확률값을 그대로 가중치로 쓰기

핵심 아이디어: "확률 X 이상만 차선"이라는 이분법 대신, 확률값 자체를 가중치로 써서
연속적으로 반영한다.

- **무게중심**: 지금 `cv2.moments(band, binaryImage=True)`로 이진 마스크의 픽셀 개수
  기반 무게중심을 구하는 대신, `sum(x * p) / sum(p)`(p = 각 픽셀의 ll 확률)로 계산한다.
  확신이 높은 픽셀이 더 크게, 낮은 픽셀은 덜 반영되되 완전히 0이 되진 않는다.
- **"이 밴드에 ll이 있는가" 판정**: 지금 `DL_LL_SIDE_MIN_PIXELS`(이진 픽셀 개수)로 보는
  대신, 확률 합(`sum(p)`)이 어떤 문턱을 넘는지로 바꾼다. 여전히 문턱은 필요하지만("있다/
  없다"는 결국 어딘가에서 결정해야 함), 개별 픽셀의 온오프가 아니라 전체 신호 강도에
  대한 문턱이라 훨씬 부드럽게 반응한다.
- **`_clip_da_by_ll()`의 경계 판정**: 마찬가지로 "이 컬럼에 ll이 있는가"를 이진값 대신
  확률 합/피크로 판단하도록 바꿀 수 있다.

## 구체적으로 바뀌어야 할 곳

- `perception/dl_lane.py`
  - `detect()`: `ll_mask = (ll_roi >= DL_LL_FG_THRESHOLD) * 255` 이진화를 없애고, `ll_prob`
    (float, 이진화 전)를 그대로 아래로 넘긴다. `ll_coverage`(sanity check용) 계산도 이진
    픽셀 비율 대신 확률 합 기반으로 바꿔야 함.
  - `_ll_slice_centers()`: 좌/우 탐색창 안에서 `cv2.moments(band, binaryImage=True)` →
    확률 가중 좌표 계산으로 교체. `DL_LL_SIDE_MIN_PIXELS` → 확률합 기반 문턱으로 교체.
  - `_clip_da_by_ll()`: `np.nonzero(np.any(ll_mask[...] > 0, axis=0))` 같은 이진 컬럼 판정을
    확률 기반으로 교체.
  - `_ll_decay_mask`(§2.14, 잔상): 이미 float 누적이라 오히려 이 방식과 자연스럽게 더 잘
    맞을 가능성이 있음(원래 확률처럼 연속값을 다루는 구조).

## 적용 범위 — da(주행가능영역)엔 적용 불가

**이 방식은 ll 파이프라인에만 해당한다.** da 쪽(`_largest_da_component()`의 시드/연속성
선택, §2.11)은 `cv2.connectedComponentsWithStats`가 구조적으로 이진(또는 라벨) 마스크를
요구하므로 그대로 이진화가 필요하다. da는 건드리지 않는다.

## 장점

1. 확률 경계 근처 노이즈로 인한 프레임 간 온오프 흔들림이 줄어든다(연속적 반영).
2. "근거리엔 관대하게, 원거리엔 엄격하게"를 굳이 숫자 하나(`DL_LL_FG_THRESHOLD`)로
   타협할 필요가 없어진다 — 낮은 확신 픽셀이 자연히 덜 반영되므로.
3. 모델이 실제로 계산한 정보(확신 정도)를 버리지 않고 그대로 활용한다.
4. `_ll_slice_centers`/`_clip_da_by_ll`이 신호 강도를 더 매끄럽게 판단하게 되어, §2.14의
   가상경계가 발동하는 빈도도 더 안정적으로(급격한 온오프 없이) 결정될 가능성이 있다.

## 단점 / 리스크

1. **변경 범위가 크다** — `_ll_slice_centers`, `_clip_da_by_ll`, 관련 문턱값 전부를
   다시 써야 해서 오늘 세션에서 이미 여러 번 바뀐 이 함수들을 또 크게 흔드는 셈이다.
   회귀 위험이 그만큼 크다.
2. "있다/없다" 판정 자체가 완전히 없어지는 건 아니다 — 확률합 문턱이라는 형태로
   여전히 필요하다. 이분법 자체를 없앤다기보다 "덜 급격하게" 만드는 것에 가깝다.
3. `DEBUG_VIZ_DL_LANE`의 빨간 반투명 오버레이 같은 시각화는 여전히 "어디를 칠할지"
   결정하려면 어떤 컷이 하나 필요하다 — 계산(확률 가중)과 화면 표시(이진 오버레이)가
   서로 다른 로직을 쓰게 되어 약간의 불일치가 생길 수 있다(디버깅 시 헷갈릴 수 있음).
4. 실차 미검증 — 확률 가중 방식이 실제로 흔들림을 줄이는지는 시뮬레이션이 아니라
   실차에서 직접 비교해봐야 안다.

## 착수 조건

`DL_LL_FG_THRESHOLD` 인하(README §2.15)만으로 `ll_cov`가 정상 범위로 올라오고 흔들림도
충분히 줄어들면, 이 리팩토링은 굳이 안 해도 된다. **값 조정으로 안 되는 게 실차로
확인된 뒤에** 이 문서를 다시 열어 착수할 것.
